# KakaoTalk Reader V2 P2.1 第二輪獨立 QA

日期 2026-11-28（台灣時間）。分支 `dev/kakaotalk-native-v2`，固定候選 `961ed5ea96d0c1453d8913b2e4c601f9967e2811`，第一輪 QA `66843a439a1a997dfcb3caf17fdd6ca37bf0e54c`。以候選內容核對第一輪報告、修正說明、架構、資料模型、事件契約及核心程式。

**建議暫緩凍結 P2 契約及正式接入 P3。** 五項原始重現情境均已修正，但獨立測試找到兩個應先處理的高優先問題。可用合成資料繼續 P3 原型。

## 1. 正式回歸

Linux x86_64、Python 3.12.14、旁路 SQLite 3.53.1。官方 SQLCipher v4.12.0 原始碼建置的 CLI 及共享函式庫接入測試，CLI 回報 4.12.0 community，函式庫使用系統 OpenSSL。設定 `KAKAO_TEST_SQLCIPHER`、`KAKAO_TEST_SQLCIPHER_CLI` 後執行 `python3 -m unittest discover -s tests -v`。**40／40 通過、零跳過，0.582 秒。** 兩個加密案例分別驗證真實合成 WAL／錯誤金鑰與真實收據。錯誤金鑰案例的 SQLCipher HMAC 訊息符合預期。

以測試方法名稱集合比對，原 29 項全數存在，新增 11 項。另檢視舊案例修改：事件格式改為 v2，寫入競爭由見證鎖拒絕，舊 schema 由顯式 adopt 遷移至 v4 並換世代，舊原始證據保存仍不推進公開水位。一般 SQLite 夾具只測引擎，兩項加密測試使用正式驅動。

## 2. 五項原始重現

| 案例 | 預期、獨立重現與結果 |
| --- | --- |
| V2-01 變更批次 | 同一訊息連續三次修改狀態，由原快照水位取批次。預期在固定結束水位只出現一份最新物件及所需關係。實測只出現一份；之後新增交易仍不改變已物化分頁。以合成 SQLite 客戶端套用，完整快照加兩輪批次和最後完整投影相等。**通過。** |
| V2-02 舊來源獨有歷史 | 用 preserve_legacy 保留簡單私人證據，再以 publish_legacy 發布審核欄位。預期快照只含審核欄位、發布進位且可增量取得。實測歷史進入快照與批次，沒有私人欄位，歷史異動觸發整組替換。**原情境通過。** 相同來源內不同身分另見 R2-01。 |
| V2-03 非正文變更 | 初始翻譯後依次變更 status、scope、引用與作者名。預期譯文仍有效。實測翻譯投影相同；改正文後舊翻譯不再輸出，原工作提交遭拒。獨立建 v3 樣本含有效及過期譯文，adopt 後保留有效譯文並換世代。**通過。** |
| V2-04 舊備份及同水位分岔 | 留早期備份，寫入新事件後單獨還原 SQLite，預期拒絕。另建固定事件時間、同世代、同序號、同欄位但不同正文的分支，測試見證拒絕不同鏈尾。兩者均拒絕；正式還原可旋轉世代，舊游標需完整快照。**原情境通過。** 實際崩潰後還原見 R2-02。 |
| V2-05 重新封存舊 A | 以 SQLCipher 建立 A，原生 ID 不變下改為 B。正常簽發的 B 應同步，重新封存 A 應保留 B。實測正常更新成功，重封 A 拒絕且旁路快照不變。**通過。** |

## 3. 新保護機制及缺陷

### External Witness

用子程序呼叫實際 Repository，在指定的見證寫入／確認邊界注入 `os._exit(71)`，重開檢查 SQLite 與見證。

| 中斷或異常 | 預期及實測 |
| --- | --- |
| 見證預留前 | 舊交易可回滾，實測重開仍是舊正文。 |
| 預留後、SQLite 提交前 | 不確定時停止，實測拒絕開啟，未接受分岔。正式恢復出現 R2-02。 |
| SQLite 提交後、見證確認前 | 匹配預留點應能確認，實測重開完成確認並保留已提交正文。 |
| 見證缺失、JSON 損毀、舊庫替換或同世代同水位不同歷史 | 全部應拒絕，實測全拒絕。 |
| 正式還原，預留後換檔前中斷 | 應停止並可重試正式還原，實測拒絕現況，重試完成新世代。 |
| 正式還原，換檔後確認前中斷 | 應確認已匹配新庫，實測恢復備份正文及新世代，舊世代游標要求完整投影。 |

**R2-02，高，阻擋無人值守恢復。** 在正常同步交易內先改正文，讓見證的 pending 確實落盤，隨即中止子程序。正式重開拒絕符合預期；接著呼叫 `Repository.restore` 時，殘留的 SQLite rollback journal 使其回報「Close and recover the repository's SQLite sidecars before restore」。單純正式重開未讓 journal 消失。一旦在一次性合成庫以隔離的 SQLite 交易完成 journal 清理，正式還原成功並換世代。這項隔離操作只用來驗證阻礙所在。應驗收一條不用人工編輯 SQLite 即可完成的恢復路徑。

### Capture Receipt

以真實 SQLCipher 合成庫核對 A→B、當前收據重跑零變更、舊收據重播、舊 A 重新封存、移植 B 收據至 A、修改 B manifest 的時間。四種過期或不符來源均拒絕。僅指定接受新世代不足以喚回外部副本；同時顯式開啟外部恢復後可在新來源世代對帳。以新 inode 替換原本綁定檔案時，舊綁定拒絕擷取，同世代重新綁定拒絕；明確綁定新世代後可擷取並同步。結果符合預期。收據證明本機有序擷取，KakaoTalk 上游內容新鮮度仍無獨立證明。原地改寫相同 inode、資料庫與見證同時回退不在此保證內。

### Legacy Projection

**R2-01，高，阻擋完整歷史契約。** 在同一份合成 app-export 中建立三筆經審核歷史，ID 各異，正文與暱稱相同。前兩筆具有完全相同的精確秒時間，第三筆用涵蓋該秒的分鐘時間。預期保留同一來源的不同訊息身分，時間交疊僅作跨來源相似線索。實測原始證據存三筆，快照只可見一筆。以補載方式加入兩筆不同原生 ID 時，原生訊息仍各自存在。原因是 refresh_legacy 對正文、暱稱及時間交疊抑制顯示，沒有同一份來源的已知不同身分例外。即使這符合目前文件描述的保守抑制，仍不符合本輪要驗證的完整歷史行為。

另測秒與分鐘交疊、後續原生補載、暱稱更改及人工映射。新暱稱不匹配時原生與歷史各自保留；改回可精確匹配暱稱後，歷史列退出並推進替換水位。將同一歷史書籤映射到兩個原生 ID 時保留兩項映射並標為歧義，私人證據依然留在本機、無輸出至快照。暱稱不同時能暫時同時顯示兩份，需審核映射才能解決。

### Consistent Change Batch

獨立用 SQLite 客戶端夾具驗證逐頁接收、同一物件多版本折疊、物化後新交易不改寫舊頁、空增量無紀錄、歷史／映射整組替換（包含空的歷史列表），以及錯世代或超前游標要求完整投影。重複頁、缺頁、逆序、混批被夾具拒絕。半批刻意中斷後投影與游標一同回滾，完整重試可與最新完整快照逐集合比對一致。實際事件保留期清除未實作。這次證明本機批次可以供遵守契約的消費端使用，網路傳輸驗證與正式客戶端仍屬 P3／P5。

## 4. 驗收限制與決策

此 Work 環境無授權 Mac 原生副本，未對正式 App 進行操作，亦無以 CSV 或 OCR 作替代。實機長期常駐、並行原生讀取、休眠補抓、真正斷電及上游時序未測。所有獨立故障注入只使用隔離的合成資料。

五個原始案例的修正有效。R2-01 會隱藏已知不同身分的歷史訊息，R2-02 會在實際中斷後阻斷正式還原。先處理兩項並重跑，再決定凍結資料契約及正式接入 P3。
