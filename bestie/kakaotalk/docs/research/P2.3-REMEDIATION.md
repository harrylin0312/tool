# P2.3 還原並行控制修正

基準為 `fd1542a2e31c953b5aac8a979346eb6018c7b882`。本輪處理第三輪獨立 QA 的 R3-01。基準版已用獨立程序重現無 rollback journal 時，有活躍讀取或寫入交易仍放行還原。 [第三輪 QA](P2-QA-REPORT-ROUND3.md)

## 交易與見證順序

1. 取得外部見證鎖，驗證備份，建立並同步寫入新世代的候選檔。
2. 若舊資料庫有 rollback journal，先由 SQLite 在 rollback 模式下恢復。確認恢復端點符合現有見證的 committed 或 pending，再以 SQLite 正常提交清理冷 journal。外部見證鎖持續保留。
3. 對現有檔與候選檔取得零等待的 `BEGIN EXCLUSIVE`，確認都是 rollback 模式並拒絕殘留 WAL／SHM。若剛完成 journal 恢復，在舊檔的最終獨占交易中再次核對恢復端點。若其他交易搶先持鎖、journal 重現或端點變更，拒絕換檔。
4. 保持兩個獨占交易開啟，寫入見證 pending、原子換檔、同步父目錄，再確認見證。兩個交易隨連線關閉而結束，外部見證鎖最後釋放。候選檔在自己的 inode 上已持鎖，因此換檔後到見證確認之間仍會拒絕 SQLite 交易。
5. 在換檔前崩潰時，未完成的見證預留會讓一般開啟拒絕，操作者可重新執行正式 restore。換檔後崩潰時，重新開啟會查核新檔和 pending 端點，再確認見證。成功還原後，舊世代游標需要完整快照。

## 操作邊界

受控服務先停止接收工作、等交易結束並關閉連線，再執行 restore。成功後重新開啟 Repository 並恢復服務。見證鎖會拒絕還原期間的新操作。受控的舊 Repository 控制代碼會在下一次操作驗證時拒絕使用舊 inode。SQLite 的鎖只保護持鎖交易，無法可靠辨識已開啟但未持鎖的外部連線，也無法阻止外部工具直接換檔。外部 SQLite 連線不屬於支援的操作方式。 [本機操作指南](../../native-v2/README.md)

## 驗證結果

macOS 27.0 arm64、Python 3.14.5、SQLite 3.53.2、SQLCipher 4.12.0。全部 52 項通過，涵蓋原有 46 項及 6 項新增回歸，含兩項使用真正 SQLCipher 的合成加密測試。完整測試約 1.15 秒。新測試使用獨立程序持有實際 SQLite 交易，覆蓋無 journal 的讀寫拒絕、換檔前後的競爭、還原期間的新 Repository 操作、正常還原與舊連線／游標、換檔前後的程序異常終止，以及無 sidecar 的 WAL 模式拒絕。原有測試保留冷／熱 journal 與不符合見證端點的案例。既有見證測試改在手動取得見證鎖前讀取水位，以符合 Repository 讀取也須協調的規則，既有斷言維持原樣。實驗使用旁路合成資料庫，未接觸 KakaoTalk 原始資料。
