## R2-02 崩潰還原

| 情境 | 獨立驗證結果 |
| --- | --- |
| 原始冷 journal | 實際子程序在見證 pending 落盤後、SQLite 提交前以 os._exit 終止。普通重開安全拒絕，直接呼叫正式 restore 成功。無須手動處理 SQLite 或刪 journal。 |
| 熱 journal | 縮小頁快取、大量寫入後在同一邊界終止。讀取 journal 確認存在 SQLite 有效熱標頭，未先開啟旁路庫，直接正式還原成功且 journal 由 SQLite 清理。 |
| 見證端點 | 原崩潰情境驗證匹配 committed。另以合成 pending 端點及未提交 journal 檢查，也可成功還原。把合成見證兩端都設為不符時安全拒絕且見證內容維持不變。 |
| 再次中斷 | 正式還原在新見證已預留、換檔前中斷，重新執行正式還原可完成。換檔後、確認前中斷，重開匹配 pending 並保留備份內容。正常交易在 SQLite 提交後、確認前中斷，也可重開確認。未另注入 SQLite 熱回滾函式內的真正斷電。 |
| 世代和游標 | 還原後世代不同，舊游標要求完整快照。 |
| 活躍程序 | 透過 Repository 持有見證鎖時拒絕。無 journal 的直接 SQLite 讀取交易則未被拒絕，見 R3-01。 |

### R3-01　活躍 SQLite 讀取交易未阻擋正式還原

**高，阻擋本輪契約凍結。** 在一次性測試庫建立正常備份。由另一個程序用 SQLite 開啟旁路庫，執行 BEGIN 並查詢 metadata 中的 generation，保持交易不結束。確認現場沒有 rollback journal，主程序呼叫 `Repository.restore`。預期因活躍程序而拒絕。實測 restore 成功並回傳新世代，子程序在同一讀取交易再次查詢時仍看見舊世代。此時新舊資料庫已有不同檔案身分。程式只在存在 rollback journal 時嘗試 SQLite 獨占交易，持有見證鎖能攔住新 Repository 操作，但無法涵蓋上述直接連線。應明訂可執行的連線協調邊界，並重跑沒有 journal 的活躍讀取案例。

## 既有缺陷及驗收限制

未發現 V2-01 至 V2-05 原始故障回歸。獨立重跑包含固定批次水位及投影等價、舊歷史匯出、非正文變更保持譯文、舊備份與同水位分岔拒絕，以及用真實 SQLCipher 的 A→B、重封 A 拒絕及顯式新世代恢復。

本環境未使用 Mac 原生資料或正式 KakaoTalk App。實機長期常駐、並行原生擷取與休眠補抓依原驗收範圍處理，不影響本輪隔離測試判定。除 R3-01 外，跨暱稱相似資料的人工審核及大資料集效能量測可列後續待辦。
