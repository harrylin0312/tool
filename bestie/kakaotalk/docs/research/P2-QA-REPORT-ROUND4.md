## 2. R3-01 獨立複驗

獨立探針在臨時旁路庫寫入兩版正文並保存較舊備份。使用不同程序持有 SQLite 交易。換檔測試於見證 pending 持久化後及見證確認入口停止流程、啟動競爭程序，並以 inode 驗證當時路徑指向舊檔或新檔。

| 測試 | 預期及實測 |
| --- | --- |
| 無 journal 的活躍讀取與寫入 | 子程序分別以 BEGIN、BEGIN IMMEDIATE 取得交易並讀取 metadata。兩者皆拒絕還原。inode、見證位元組及完整投影與先前一致，世代與事件水位未變。 |
| 換檔前 | 見證已寫入 pending，仍指向舊 inode。其他程序讀取和寫入均回 SQLITE_BUSY，新 Repository 開啟也被見證鎖拒絕。 |
| 換檔後、見證確認前 | 路徑已指向新 inode。其他程序讀寫仍返回 SQLITE_BUSY，新的 Repository 仍被拒絕。 |
| 無活躍交易 | 正式還原完成並讀到備份正文，新世代不同於舊世代。舊 Repository 的 snapshot、state、watermark 及持久化寫入均被拒絕。新開啟可用，舊世代游標要求完整快照。 |
| WAL 模式、無 WAL／SHM | 連線全部關閉且兩個 sidecar 不存在時仍拒絕。資料庫和見證位元組一致。 |

候選檔先關閉建檔連線並完成 fsync，才取得獨占鎖。舊檔與候選檔的 SQLite 連線留在同一個 ExitStack，跨越原子換檔、父目錄 fsync 和見證確認，之後才依序關閉，見證鎖最後釋放。期間未對任一資料庫 inode 額外開關檔案描述符。journal 恢復交易與最終獨占之間有重新取鎖的區段。受控 Repository 仍受見證鎖排除，最終換檔前會再次檢查 sidecar 與剛恢復的端點。實測兩個換檔邊界均無競爭交易進入。

## 3. 故障恢復與既有七項缺陷

| 範圍 | 結果 |
| --- | --- |
| R2-02 冷、熱 journal | 重跑實際子程序在 pending 後異常結束的冷 journal 及已落盤、有有效熱標頭的熱 journal 情境。兩者用正式 restore 完成。見證端點不符的正式測試拒絕且保留見證。 |
| 兩個換檔崩潰邊界 | 獨立注入程序於換檔前、後終止。換檔前普通開啟拒絕，重跑正式還原可完成。換檔後重開確認 pending 並保留備份內容。全程沒有手動刪除 journal。 |
| V2-01 固定水位 | 實測較新交易不改變舊批次，完整快照套用增量後與最新投影一致。 |

## 4. 凍結與後續驗收

P3 應使用受控 Repository。正式服務還原前須停止收件、等現有交易結束、關閉受控連線並進入維護模式。還原後重開連線及重取完整投影。未持鎖的外部閒置 SQLite 連線及不遵守協調的直接檔案操作，依既有支援邊界處理。正式服務的維護流程整合、大資料集效能與上述 Mac 實機項目列入後續驗收。
