# 待研究方案｜Mac 本機檔案／資料庫擷取

更新：2026-11-28。擁有者確認這是下一階段第一優先；串流為最後階段。原生資料已確認為未來主要來源。R4 已驗證隔離副本與合成 WAL，實際 App 生命週期及長期效能仍待驗收。

## 問題與假設

現行 CSV／TXT 能取得文字，卻沒有結構化回覆；逐頁 OCR 成本高且有配對歧義。若 KakaoTalk Mac 的本機資料可合法、唯讀取得指定聊天室的原生 ID、正文、時間及回覆 ID，便可能省去大量畫面掃描。已在指定 Open Chat 讀出結構化資料及討論串關係。現有 CSV、OCR、模型衍生表格與 HTML 各自為有範圍限制的參考來源。

## 研究步驟與驗收

1. **R1 靜態審查**：查證候選的確切 commit、版本、Mac／KakaoTalk 需求、讀取架構、SQLCipher 相容性、回覆與 Threads 欄位、資料留存與安全風險。輸出比較表及推薦唯讀方法。
2. **R2 本機 PoC**（需 Mac 可用及擁有者授權）：只讀指定 Open Chat 少量已知訊息，檢查原生訊息 ID、作者識別、完整時間、正文、類型、引用目標、討論串、刪除／不可載入狀態。禁止發送或修改；不提交私人內容。
3. **R3 正確性測試**：以來源已標記的 App 匯出、舊 HTML、原生資料與 App 畫面作獨立比對，人工核對正負例、同秒同作者同文、截短引用、舊目標、跨日、事件、不可用目標與 Threads。報告覆蓋率、正確／錯連、缺漏、重複、未確認數，區分參考集自身可能不完整；錯連不可接受，不宣稱 100% 覆蓋未測區域。
4. **R4 增量擷取驗證**：同一批重跑、重啟、分頁、快速新訊息、離線後補抓、刪除／修改事件、App 版本變動。量測每批耗時、每秒訊息、CPU／記憶體、錯誤及缺漏；和原 OCR 方式同範圍比較。資料讀取應具一致性，不直接讀取不一致的 SQLite/WAL 副本。
5. **決策門檻**：可證實安全、可靠的原生 ID 與回覆關係才進入正式 adapter 開發；若僅能讀正文，則保留 OCR／Threads 作回覆補充；若不相容或權限風險不可接受，停止該方案。不要以猜測替代資料。

## R4 選型與共同架構

採索引游標加重疊區與週期性對帳。採檔案監聽加輪詢，事件只觸發一致性查詢。原生連線、正規化、同步和事件紀錄供批次與未來串流共用。詳見 [增量研究](research/INCREMENTAL-EXTRACTION-REPORT.md) 和 [第二代設計](research/NATIVE-EXTRACTOR-DESIGN.md)。

## 未來統一資料模型（提案）

以穩定內部 ID 保留既有 mNNN，不用原生 ID 直接重編網頁。保存 source、來源原生 ID（可空）、來源排序、原始時間及 precision（second/minute/unknown）、作者、正文、事件類型、回覆目標／線索、確認狀態、譯文與來源證據。不同來源的身份映射與游標分開管理，可靠映射才合併。原生 ID 若確實可用，仍須與舊 CSV／HTML 唯一對應，不能靠數字偏移。原文、回覆與翻譯可獨立更新。

## 備援：手機 TXT + 回覆畫面

已在 Gmail 實測透過原始 MIME 提取 ZIP、CRC32 核對並解壓，普通附件 API 不支援 ZIP。手機 TXT 匯入器尚待開發：辨識中文日期時段、系統事件、多行正文、同分鐘重複、與 CSV 重疊序列；保留分鐘精度，不偽造秒數、不改可信歷史雜湊。回覆如有需要從錄影／截圖或 Mac Threads 補抓，抽幀去重與 OCR 亦未驗收。先研究本機擷取；此方案為無 Mac 時的備援，不與主研究搶優先序。

## 不在本階段範圍

即時串流、對外伺服器、SSE、遠端存取、常駐代理、全自動翻譯發布，都等擷取與資料模型穩定後再做。舊 [串流設計](../live-sync.md) 保留供最後階段重新評估。
