# KakaoTalk 原文發布工具獨立驗收

驗收日期為 2026-11-28（台灣時間）。候選版本為 `234aa56fd0130ab7de4d71c17bb8ada86f9aca8f`，測試分支為 `test/kakaotalk-cross-batch-replies`。

**建議暫緩合併 main。** 以舊翻譯快照重新初始化會覆蓋較新的原文輸出，已用正式資料的隔離副本重現。首次遷移也會接受一份與原文歷史正文不符的 CSV，寫入雜湊後再拒絕正確的原始 CSV。另有新建引用折疊原文換行的顯示差異。

## 環境與方法

- Linux x86_64，Node.js v24.22.3，npm 11.19.1，Python 3.12.14，npm 官方套件 `linkedom` 0.18.15。候選分支未提供 Node 套件鎖檔。
- 先讀取 `HANDOFF.md`、`storage-workflow.md` 和 `live-sync.md`，再在候選 commit 執行 `node live/test-publish-original.mjs` 與 `node live/test-publish-integration.mjs`。兩支均通過，整合測試亦解密輸出並檢查 DOM。
- 私下取得完整加密 CSV 與原文快照的解鎖資訊。兩份密文與驗收時 main 的對應 Git blob 相同。分別以 AES-256-GCM 驗證並解密。使用 2,457 列正式 CSV 跑首次遷移及重跑，再在其副本加入 7 列測試資料，第三批再加 1 列。每輪解密原文候選，比對結構、來源欄位、前後向連結、歷史資料及密文檔案。
- 以 Headless Chromium 158.0.8127.0 透過 localhost 執行實際加密閱讀器。採 390×844 觸控視窗與 1440×900 桌面視窗，比對渲染樣式和尺寸，並操作跳轉及書籤。故障案例使用個別快照副本，私人資料與驗收用程式均留在隔離工作區。

## 可重現問題

### QA-01　雙 CSV 初始化會覆蓋較新的原文快照

**嚴重度高，阻擋合併。** 在隔離資料夾以已有較新輸出的 `original/index.html` 為基準，保留候選 commit 同目錄的舊翻譯快照 `index.html`。從正式 CSV 取與舊翻譯版截止相符的前 1,380 列存為 `previous.csv`，再取前 1,381 列存為 `current.csv`。執行 `node live/publish-original.mjs current.csv previous.csv`，由 stdin 傳入原有金鑰。

預期拒絕歷史回退，保留既有輸出。實際執行成功，解密輸出的 CSV 計數從 2,465 降到 1,381，訊息或事件 ID 從 2,467 降到 1,383，回覆從 218 組降到 71 組。單是正式原文基準就有 1,076 個既有 ID 在回退後消失。另在內建合成整合資料上重現相同狀況。雙 CSV 模式會以舊翻譯頁為基底，覆寫前未檢查目前原文頁的進度。

### QA-02　首次遷移接受與既有歷史不符的 CSV，之後拒絕正確來源

**嚴重度高，阻擋合併。** 使用沒有 `data-export-digest` 的正式原文快照副本。將完整 CSV 中一筆原本可唯一映射的歷史一般訊息改一小段正文，保留所有列數、作者與時間。使用單 CSV 模式先跑修改副本，再跑未改動的正式 CSV。

預期確認既有正文可對應後才寫入，遇到不一致時保留原有輸出。實際首次遷移成功並換了密文。原文節點仍在，該筆失去來源映射，程式卻將修改後的 CSV 固化為前綴雜湊。下次使用未改動的正式 CSV 時，程式以「歷史 CSV 內容已變更」拒絕。

### QA-03　新建引用會折疊原文的換行

**嚴重度中。** 在正式 CSV 副本附加包含兩行短文字的訊息，再附加一則經審核引用它的回覆。發布後解密，於桌面寬度查看較短、可完整放在同一行的引文。

預期引用保留原文的分行。實際原文 DOM 有正文行間的 `<br>`，引用只在作者和正文之間有 `<br>`，正文是單一文字節點。`.quote` 的 `white-space: normal` 使換行折疊，桌面瀏覽器實測正文只佔一行。手機上的兩行來自欄寬自動折行。
