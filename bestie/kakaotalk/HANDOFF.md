# KakaoTalk 韓中對照聊天室｜專案交接

更新日期：2026-11-26（台灣時間）

## 接手目標

讓使用者用 Mac 上已登入的 KakaoTalk 讀取指定 Open Chat 聊天室，在 iPhone 或電腦瀏覽器看到原文、繁中翻譯和完整的回覆脈絡。Mac 可選擇開啟即時擷取，使用者在外面用私人連線看更新。Mac 離線時，仍可用 GitHub Pages 開啟已發布的加密快照。

使用者希望直接打開網址就能閱讀，不必每次手動匯入 HTML、聊天檔或截圖。介面沿用目前的聊天時間線，包含手機與電腦各自的排版、頭像、暱稱、時間、原文與繁中譯文。一般訊息、加入／離開等系統事件、聊天室安全提示要能一眼區分。此專案中的「回覆」是保存和瀏覽回覆關係，包含從原訊息查回覆與從引用回到原訊息。

## 已證實的擷取方式

- **歷史正文可以批次掃描。** 實作前的驗證是用工具操作 Mac KakaoTalk，逐頁讀 macOS 輔助使用介面。訊息列能讀出暱稱、正文、時間和部分系統事件。這次操作成功產出 446 筆快照；當時沒有對每頁做獨立漏抓率或延遲量測。頁面有時保留在原地，重新把焦點放回訊息區並核對前後重疊內容後才繼續翻頁。
- **引用需要不同的資料來源。** 主聊天室的輔助使用樹未可靠提供 `Reply to` 的作者、被引用正文或目標 ID。前幾輪用工具逐頁截取 KakaoTalk 視窗，從畫面讀暱稱和引用片段，再用 Python 批次配對。同暱稱、較早發出且正文能唯一配對時才建立跳轉。截短引用可用前綴比對。Threads 面板可直接從介面讀出討論串原訊息及回覆，已核對兩組。
- **目前的回覆數量有明確邊界。** 71 組是這份快照已核對的關係。KakaoTalk 顯示「原訊息無法載入」的回覆仍保留正文及狀態。已完成歷史快照的回覆補查。即時自動讀取、快速刷屏時的漏抓率、鎖屏及最小化的行為仍需實機測。
- **初始匯出需求已完成。** 使用者要求先保存目前內容，再把即時擷取做成可選功能。曾遇到網頁解密後空白，原因是舊版透過 blob iframe 顯示。現在解密後將 `style` 和 `main` 直接掛到頁面，並攔截站內跳轉。此流程曾在線上驗證。

## 交接給下一位的實作順序

1. **先做可重跑的本機匯入。** 依 [即時同步設計](./live-sync.md) 把工作資料放在 `~/Library/Application Support/KakaoTalkReader/` 下的 SQLite。保留來源排序和原本的 `m{index}` 對應。從 HTML 的 `article[id]` 取正文附屬資訊、譯文、頭像及引用，從 `a.quote[href="#m…"]` 還原回覆關係，從 `data-reply-state="unavailable"` 還原未載入狀態。用回覆表重新生成反向清單。匯入兩次後，快照筆數、引用關係和既有翻譯應一致。
2. **用本機試跑驗證新訊息擷取。** 先保留針對指定聊天室的啟停和狀態。利用輔助使用介面讀正文，測試變更通知並保留定時檢查。用受控的連續訊息、同一分鐘重複正文、超過一頁的新訊息及重啟測試，確認順序、去重和補抓。使用者先前提供的 Mac 是 Apple Silicon M3。可把 LM Studio 當本機翻譯候選，實測韓文、英文和混合內容後再決定。
3. **補上自動回覆辨識。** 先驗證 Threads 資料，再用 ScreenCaptureKit 擷取指定聊天室並測試 Vision OCR。引用辨識失敗時要存「待確認」；保留可確認的暱稱、片段和資訊來源。回覆本身先入庫，後續配對或翻譯回來時更新同一筆。對重複候選需保留未確定狀態。量測前景、背景、最小化和鎖屏時的正文擷取與 OCR，兩者可能有不同結果。
4. **把網頁留在 Mac，從 iPhone 驗收遠端。** 網頁和唯讀資料介面由同一個本機來源提供，使用 SSE 接收更新。原文先顯示，繁中翻譯完成後更新。事件與訊息同一交易寫入，Safari 重連後依事件序號補，且保留閱讀位置。經 Tailscale Serve 提供私人 HTTPS，驗證 iPhone 關 Wi‑Fi 後能連上，授權範圍外無法讀取。Mac 睡眠時停止即時服務，醒來後查歷史補抓。找不到舊游標時需標示可能缺漏的時段。
5. **最後接上快照發布。** 使用者可手動發布，另設明確選項「結束擷取時自動發布」，有變更才上傳。即時聊天透過 Mac 更新。GitHub Pages 快照用於離線時閱讀，顯示產生時間與快照涵蓋範圍。部署成功前保留上一個已發布版本。

## 如何安全更新現有快照

1. 修改和檢查明文 HTML 都在本機進行。參考此次基準測試：71 個正向引用、71 個反向連結、1 個無法載入狀態，所有可點連結都有存在的目標。
2. 現有網頁的 `snapshot` 有兩欄，`nonce` 和 `ciphertext`。用既有 AES‑256‑GCM 金鑰、每次新產生的 12 位元組 nonce 加密完整 UTF‑8 HTML。部署格式是 Base64 編碼的 nonce，以及 Base64 編碼的密文加 16 位元組驗證標籤。金鑰從使用者既有專用網址的 `#fragment` 帶入，由瀏覽器在本機解密。使用原金鑰可以保留既有專用連結。
3. 更新 `main` 上的 `bestie/kakaotalk/index.html` 時，用當下的 blob SHA 進行版本檢查，保留解密與頁內跳轉程式。原始 JSON、明文 HTML、圖像原檔、擷取日誌、金鑰及完整解鎖連結都留在擁有者授權的私人位置。部署檔和交接文件只包含已核准提交的內容。
4. 等 Pages 部署完成，使用擁有者的專用連結打開網頁。必要時使用 `?build=<commit-short-sha>#<key>` 避免讀到舊快取。驗證引用互跳、引用翻譯、頭像、手機排版與無金鑰時的提示。頁內引用切換須保留原有 URL fragment，避免覆蓋解鎖金鑰。

完成判準是 Mac 已穩定保存新訊息，回覆關係有可核對的證據，Safari 在切換網路後能完整接續，且使用者能控制擷取和快照發布。現有的 GitHub 版本是已驗證可閱讀的加密快照，即時版仍以實機測試結果為準。

## 原文發布候選：跨批次回覆

`live/publish-original.mjs` 使用完整 CSV 及 `reply-mapping.mjs` 核對歷史原文，不以列號推算舊 ID。新訊息保存來源列號、完整時間及單列雜湊，歷史僅在唯一匹配後補上。完整前綴雜湊於首次遷移後用於防止後續歷史內容變動。原始快照的既有時間尾端 anchor 仍須先核對；未映射資料不得自動猜測。回覆審核檔仍接受原有 `[[[timestamp,name],[timestamp,name]]]` 格式，也可用 `[timestamp,name,body,rowNumber]` 消除 CSV 歧義（rowNumber 從 1 起算）；若 HTML 映射不唯一、舊引用衝突或順序不符，停止寫入並保留上一版，待人工確認。CSV 不含引用資料，不自動推測。執行 `node live/test-publish-original.mjs` 驗證純映射邏輯；正式發布前仍需以實際 linkedom 執行 CSV、驗證雙向跳轉及手機排版。不得提交 CSV、審核檔、明文或金鑰。

真實匯出可包含日期、暱稱皆空的系統紀錄；保留為原文事件，不補造時間、不加入回覆映射、不產生空日期分隔。快照截止取最後一筆具時間的紀錄。首輪遷移的來源映射不完整時仍不猜測，請保留原始 CSV。
